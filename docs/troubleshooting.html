升級失敗Upgrade failuresアップグレードの失敗

升級每次都停在 git，而且重跑幾次都一樣 Every upgrade stops at git, and re-running changes nothing アップグレードが毎回 git で止まり、何度やり直しても同じ

fatal: Not possible to fast-forward, aborting. fatal: refusing to merge unrelated histories

本機的原始碼歷程已經無法快轉到遠端（有人在機器上改過並提交、淺層 clone、或上游歷程被改寫）。因為升級用的是 git pull --ff-only，而且腳本開了 set -e，它會停在第一步：備份、遷移、建置、重啟全都沒跑，所以每次重跑都停在同一個地方。 The local source history can no longer fast-forward onto the remote (someone committed an edit on the box, a shallow clone, or upstream history was rewritten). The upgrade pulls with git pull --ff-only under set -e, so it stops at step one (no backup, no migration, no build, no restart), and every re-run stops in exactly the same place. ローカルのソース履歴がリモートへ早送り（fast-forward）できなくなっています。原因は、このマシン上で誰かが編集をコミットした、浅いクローンだった、上流の履歴が書き換えられた、のいずれかです。アップグレードは set -e の下で git pull --ff-only を実行するため、最初の手順で止まります。バックアップもマイグレーションもビルドも再起動も行われません。リポジトリの状態が変わらない以上、何度やり直しても同じ場所で止まります。

v0.6.13 起已自動處理：升級偵測到無法快轉時，會把只存在於本機的提交保留到 upgrade-recovery/<時間戳> 分支，再重設到遠端並繼續升級。先升到 0.6.13 以上就不會再遇到。 Fixed automatically since v0.6.13: the upgrade keeps any local-only commits on an upgrade-recovery/<timestamp> branch, resets to the remote and carries on. Once you are past 0.6.13 this cannot recur. v0.6.13 以降は自動で復旧します：早送りできないと分かると、このマシンにしかないコミットを upgrade-recovery/<タイムスタンプ> ブランチに退避し、リモートへリセットしてアップグレードを続行します。0.6.13 以降に上げてしまえば、この問題は再発しません。

cd /opt/jt-ipam/frontend && sudo -u jtipam pnpm install && sudo -u jtipam pnpm build

原因在被控端之外：FreeRDP 的用戶端是用一張固定的按鍵對照表把鍵盤事件翻成 RDP 事件，沒有 Unicode 鍵盤通道，因此配置上沒有的字元送不出去。預設的 aardwolf 引擎沒有這個限制，如果目標是 Windows，用預設引擎即可。 The cause is in the client, not the target: FreeRDP translates key events through a fixed key table and has no Unicode keyboard channel, so characters absent from the layout cannot be sent. 網頁連線連不上，同一區網用 RustDesk 程式卻連得上 The web connection fails, but the RustDesk app on the same LAN connects Web 接続はつながらないが、同じ LAN の RustDesk アプリではつながる

最常見的原因是對方電腦的 RustDesk Key 設錯（例如大小寫打錯）。Key 錯的電腦照樣能向 ID 伺服器註冊（顯示「就緒」）、照樣回報主機名稱，同一區網內的 RustDesk 程式會直接連線、不經過中繼，所以也連得上；只有走中繼時會被中繼伺服器（hbbr）拒絕，而網頁連線一定走中繼，從外網用 RustDesk 程式連也一樣會失敗。RustDesk 代理 1.1.0 起會讀 hbbr/hbbs 的日誌找出這種電腦：伺服器列顯示「Key 錯誤 N」、裝置清單標「Key 錯誤」、IP 頁說明被拒的時間，網頁連線的錯誤訊息也會直接說是對方的 Key。修法：在那台電腦的 RustDesk「設定 → 網路 → ID / 中繼伺服器」把 Key 改成跟伺服器公鑰完全相同（用複製貼上）。改好之後下一次經過中繼成功，標記就會消失。日誌不在 /var/log/rustdesk-server/ 的站台（例如自己寫 systemd unit 或用容器）可以在代理的設定檔加 JT_RD_LOG_DIR= 指到日誌目錄；按「測試」會顯示讀不讀得到。 Most often the device's RustDesk Key is wrong (for example a letter in the wrong case). A device with a wrong Key still registers with the ID server (it shows "Ready") and still reports its host name, and the RustDesk app on the same LAN connects directly without the relay, so that works too; only connections through the relay are refused by the relay server (hbbr). The web connection always uses the relay, and the RustDesk app connecting from outside fails as well. From RustDesk agent 1.1.0 the agent reads the hbbr/hbbs logs to find such devices: the server row shows "Wrong Key N", the device list marks "Wrong Key", the IP page says when it was refused, and the web connection error names the device's Key directly. Fix: on that computer, set the Key in RustDesk "Settings → Network → ID/Relay server" to exactly the server's public key (copy and paste it). The mark goes away after the next successful connection through the relay. If the logs are not in /var/log/rustdesk-server/ (a hand-written systemd unit or a container, for example), add JT_RD_LOG_DIR= with the log directory to the agent's config file; Test shows whether they can be read. 最も多い原因は、接続先の RustDesk の Key の設定ミス（大文字と小文字の打ち間違いなど）です。Key が誤っていても ID サーバーへの登録（「準備完了」と表示）やホスト名の報告はでき、同じ LAN 内の RustDesk アプリは中継を通さず直接接続するので、それもつながります。中継を通る接続だけが中継サーバー（hbbr）に拒否されます。Web 接続は必ず中継を使い、外部から RustDesk アプリで接続しても同じく失敗します。RustDesk エージェント 1.1.0 以降は hbbr/hbbs のログを読んでこうしたデバイスを見つけます。サーバー行に「Key 不一致 N」、デバイス一覧に「Key 不一致」、IP ページに拒否された時刻を表示し、Web 接続のエラーも接続先の Key が原因だと示します。対処：そのコンピューターの RustDesk「設定 → ネットワーク → ID/中継サーバー」で Key をサーバーの公開鍵と完全に同じにします（コピー＆ペースト推奨）。次に中継経由の接続が成功すると表示は消えます。ログが /var/log/rustdesk-server/ にないサイト（自作の systemd unit やコンテナなど）は、エージェントの設定ファイルに JT_RD_LOG_DIR= でログのディレクトリを指定してください。「テスト」で読めるかどうか確認できます。

主控台說「這個位址不能開主控台（本機、link-local 或保留位址）」 The console says it cannot be opened to this address (loopback, link-local or reserved) コンソールに「このアドレスにはコンソールを開けません（ループバック、リンクローカル、予約済みアドレス）」と出る

IP 記錄是有子網路寫入權限的人可以自己建的，所以主控台不連本機（127.0.0.0/8、::1）、link-local（169.254.0.0/16，含雲端中繼資料位址）、多播與保留位址，避免有人建一筆 127.0.0.1 再開主控台，把 jt-ipam 當跳板連本機的服務。私網與 CGNAT（例如 Tailscale 的 100.64.0.0/10）照常可以連。主機名稱也一樣，會先解析再檢查每一個位址。真的需要例外（例如測試環境），在 /etc/jt-ipam/backend.env 的 OUTBOUND_ALLOW_CIDRS 加入該網段後重啟 jt-ipam-backend；這個設定也會放行其他對外連線，請只加需要的網段。 Anyone who can write to a subnet can create IP records, so consoles do not connect to loopback (127.0.0.0/8, ::1), link-local (169.254.0.0/16, which includes cloud metadata addresses), multicast or reserved addresses; otherwise someone could create 127.0.0.1 and open a console to reach services on the jt-ipam host. Private ranges and CGNAT (for example Tailscale's 100.64.0.0/10) work as usual. Host names are resolved first and every address is checked. If you really need an exception (a test lab, say), add the range to OUTBOUND_ALLOW_CIDRS in /etc/jt-ipam/backend.env and restart jt-ipam-backend; it also allows other outbound connections, so add only what you need. 主控台開著的期間每 30 秒會重新確認一次：帳號仍是啟用的、開主控台的那次登入沒有被登出，以及仍有這個 IP 的連線權限。帳號被停用、被強制登出（含重設雙因素驗證）、自己在別處登出這次登入，或是 IP 被刪除、連線權限被收回時，連線會在 30 秒內結束，畫面會說明是哪一種原因，並留一筆 console_revoked 稽核記錄。原因是登出的話，重新登入之後再開即可；是權限的話，請管理員確認權限設定。 While a console is open it is re-checked every 30 seconds: the account is still active, the sign-in that opened it has not been signed out, and you still have console rights on that IP. If it was a sign-out, sign in again and reopen it; if it was permissions, ask an administrator to check them. コンソールを開いている間は 30 秒ごとに、アカウントが有効であること、そのコンソールを開いたログインがログアウトされていないこと、その IP への接続権限がまだあることを確認します。アカウントの無効化、強制ログアウト（二要素認証のリセットを含む）、別の場所でのそのログインのログアウト、IP の削除や接続権限の取り消しがあると、30 秒以内に接続を終了し、どの理由かを画面に表示して console_revoked の監査記録を残します。ログアウトが理由ならログインし直して開き直してください。権限が理由なら管理者に設定を確認してもらってください。
